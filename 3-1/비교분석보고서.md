# 비교 분석 보고서 (산출물 1)

> 같은 자동화 워크플로우를 노코드 도구 2개로 구현하고 비교한 기록입니다.
> ⚠️ 캡처에 나오는 토큰, API 키, 비밀번호는 `****`로 가리고, 이메일과 채팅 ID도 일부를 가립니다.

## 2. 공통 워크플로우 설계

두 도구에서 시작 이벤트, 핵심 액션, 분기 조건, 최종 결과를 똑같이 설정했습니다.

| 구분 | 내용 |
|---|---|
| 시작 이벤트 (트리거) | 매일 아침 7시 (한국 시간) |
| 핵심 액션 | Open-Meteo에서 강남구의 오늘 날씨(최고 기온, 최저 기온, 비 올 확률)를 가져옴 |
| 분기 조건 | ① 비 올 확률 60% 이상 ② 최저 기온 0도 이하 ③ 일교차(최고 − 최저) 10도 이상 중 하나라도 해당하는지 확인 |
| 최종 결과 | 해당하는 항목을 한 메시지에 모아 텔레그램으로 보냄 / 해당 없음이면 보내지 않음 |

```
[트리거] 매일 아침 7시
   ↓
[액션 1] 오늘 날씨 가져오기
   ↓
[조건 분기] 비 / 추위 / 일교차 확인
   ├─ 하나 이상 해당 → [액션 2] 텔레그램으로 모은 알림 보내기
   └─ 해당 없음 → 종료 (알림 없음)
```

## 3. 도구별 구현

### 3-1. Make

**구현 과정 요약**

1. Make에 Google 계정으로 가입하고, 프로필의 시간대를 Asia/Seoul로 바꿈
2. 새 시나리오를 만들고 이름을 `아침 날씨 알림`으로 정함
3. **HTTP (Make a request)** 블록을 추가하고 Open-Meteo 주소를 넣음 (Method: GET, Authentication: No authentication, Parse response 켬)
4. Run once로 실행해 Status Code 200과 `Data → daily` 안의 최고 기온, 최저 기온, 비 올 확률 값이 들어온 것을 확인함
5. **Telegram Bot (Send a Text Message or a Reply)** 블록을 추가하고 봇 토큰으로 연결, Chat ID를 넣어 "테스트" 메시지가 오는지 확인함
6. 텔레그램 메시지에 날씨 값과 `if()` 함수를 넣어 해당하는 알림 문구만 들어가게 함
7. 두 블록 사이 연결선에 **필터(깔때기)**를 만들고 비 / 추위 / 일교차 조건 3개를 OR로 연결함
8. 기준값을 잠깐 바꿔서 알림이 안 가는 경우도 테스트한 뒤 원래 값으로 되돌림
9. 시계 아이콘에서 실행 주기를 **Daily 07:00**으로 정하고 시나리오를 **Active**로 켬

**사용한 주소와 수식 (참고)**

날씨를 가져온 주소

```
https://api.open-meteo.com/v1/forecast?latitude=37.5172&longitude=127.0473&daily=temperature_2m_max,temperature_2m_min,precipitation_probability_max&timezone=Asia%2FSeoul&forecast_days=1
```

텔레그램 메시지 내용

```
🌤 오늘 강남구 날씨 (최저 {{first(1.data.daily.temperature_2m_min)}}° / 최고 {{first(1.data.daily.temperature_2m_max)}}°)
{{if(first(1.data.daily.precipitation_probability_max) >= 60; "☔ 비가 올 수 있어요, 우산 챙기세요"; "")}}
{{if(first(1.data.daily.temperature_2m_min) <= 0; "🧣 많이 추워요, 따뜻하게 입으세요"; "")}}
{{if(first(1.data.daily.temperature_2m_max) - first(1.data.daily.temperature_2m_min) >= 10; "🧥 일교차가 커요, 겉옷 챙기세요"; "")}}
```

필터 `알림 조건` (OR)

| 조건 | 값 | 연산자 | 기준 |
|---|---|---|---|
| 비 | `first(1.data.daily.precipitation_probability_max)` | 이상 (Greater than or equal to) | 60 |
| 추위 | `first(1.data.daily.temperature_2m_min)` | 이하 (Less than or equal to) | 0 |
| 일교차 | `first(1.data.daily.temperature_2m_max) - first(1.data.daily.temperature_2m_min)` | 이상 (Greater than or equal to) | 10 |

### 3-2. Activepieces

**구현 과정 요약**

1. Activepieces에 Google 계정으로 가입함. 브라우저 자동 번역이 켜져 있어 화면 오류(removeChild)가 나서, 이 사이트는 번역하지 않도록 끄고 영어 화면으로 진행함
2. Personal Project → Build a Flow → Start from scratch로 새 플로우 `아침 날씨 알림`을 만듦
3. **Schedule (Every Day)** 트리거를 넣고 매일 7시, 시간대 Asia/Seoul, 주말에도 실행으로 설정함
4. **HTTP (Send HTTP request)** 블록에 Make와 같은 Open-Meteo 주소를 넣고(Method: GET) Test step으로 날씨 값을 확인함
5. 일교차를 조건 칸에서 바로 계산할 수 없어 **Math Helper (Subtraction)** 블록으로 최고 − 최저를 먼저 계산함
6. **Router** 블록을 넣고 Branch 1에 비 / 추위 / 일교차 조건 3개를 Or로 연결함. Otherwise는 비워 둠 (조건에 안 맞으면 아무것도 안 함)
7. Router에 "이상/이하" 연산자가 없어 "초과/미만"으로 바꾸고 기준값을 조정함
8. **Telegram Bot (Send Text Message)** 블록을 Branch 1 안에 넣고 봇 토큰으로 연결함. 날씨 값이 들어간 메시지에서 HTTP 400 오류가 나서 Format을 HTML로 바꿔 해결함
9. 메시지 칸에 조건 수식(if)을 넣을 수 없어서, 해당하는 문구만 모으는 부분은 AI에게 받은 코드를 **Code** 블록에 넣어 처리함 (한계기록서 [한계 1], 코드 시도 기록 참고)
10. Router 기준값을 잠깐 바꿔 Branch 1 경로와 Otherwise 경로를 모두 테스트하고, 전체 플로우(Test Flow)를 실행해 텔레그램 알림이 오는 것을 확인함
11. 기준값을 원래대로 되돌리고 Publish로 게시해 자동 실행을 켬

**사용한 조건 (Router Branch 1, Or)**

| 조건 | 값 | 연산자 | 기준 | Make 기준과 같은 이유 |
|---|---|---|---|---|
| 비 | HTTP `precipitation_probability_max` 0번 | (Number) is greater than | 59 | 비 올 확률은 정수라서 59 초과 = 60 이상 |
| 추위 | HTTP `temperature_2m_min` 0번 | (Number) is less than | 0.1 | 기온은 소수 한 자리라서 0.1 미만 = 0 이하 |
| 일교차 | Math Helper 결과 | (Number) is greater than | 9.9 | 소수 한 자리라서 9.9 초과 = 10 이상 |

## 5. 비교 항목 (5개 이상)

### 한눈에 보기

| 비교 항목 | Make | Activepieces |
|---|---|---|
| ① 화면 구성 | 동그라미 블록을 점선으로 이어 붙이는 방식 | 블록을 위에서 아래로 쌓는 방식 |
| ② 분기 설정 방법 | 블록 사이 연결선에 필터를 다는 방식 | Router 블록으로 길을 나누는 방식 |
| ③ 비교 연산자 | 이상(≥), 이하(≤)를 바로 고를 수 있음 | 초과(>), 미만(<)만 있음 |
| ④ 계산(일교차) 처리 | 조건 칸에 빼기 수식을 바로 씀 | Math Helper 블록을 따로 추가 |
| ⑤ 조건에 맞는 문구 넣기 | 메시지 칸에 `if()` 수식으로 처리 | 노코드로 안 돼서 Code 블록(코드) 사용 |
| ⑥ 테스트 방법 | Run once로 전체를 한 번에 실행 | 블록마다 Test step으로 하나씩 테스트 |

### 항목별 설명

**① 화면 구성**

Make는 블록이 동그라미 모양이고, 점선으로 자유롭게 이어 붙여요. 흐름이 한눈에 보이지만, 블록을 끌다가 연결이 엉뚱한 곳에 붙을 수 있어요. 실제로 텔레그램 블록이 HTTP가 아닌 빈 블록에 연결돼서 메시지가 안 간 적이 있었어요.
Activepieces는 블록이 위에서 아래로 차례대로 쌓여서 순서가 헷갈리지 않아요. 블록 사이의 ＋ 버튼으로 원하는 위치에 끼워 넣을 수 있어요.

**② 분기 설정 방법**

Make는 블록과 블록 사이 **연결선에 필터(깔때기)**를 달아요. 조건에 맞으면 다음 블록으로 넘어가고, 안 맞으면 거기서 멈춰요. 따로 블록을 추가하지 않아도 돼서 간단해요.
Activepieces는 **Router**라는 블록을 따로 넣어서 길을 **Branch 1**과 **Otherwise**로 나눠요. 길이 갈라지는 모양이 화면에 그대로 보여서, 어떤 경우에 어디로 가는지 알기 쉬워요.

**③ 비교 연산자**

Make에는 "이상(Greater than or equal to)"과 "이하(Less than or equal to)"가 있어서 기준값을 그대로 쓸 수 있었어요.
Activepieces에는 "초과(is greater than)"와 "미만(is less than)"만 있었어요. 그래서 같은 뜻이 되도록 기준값을 바꿨어요. 비 올 확률은 정수라서 60 이상 → 59 초과, 기온은 소수 한 자리라서 0 이하 → 0.1 미만, 10 이상 → 9.9 초과로 맞췄어요. 값이 소수 몇 자리인지 알아야 해서 조금 번거로웠어요.

**④ 계산(일교차) 처리**

일교차는 최고 기온에서 최저 기온을 빼야 구할 수 있어요.
Make는 조건 칸 안에 `최고 − 최저` 수식을 바로 쓸 수 있었어요.
Activepieces는 조건 칸에서 계산을 할 수 없어서, **Math Helper(Subtraction)** 블록을 하나 더 넣어 일교차를 먼저 계산하고 그 결과를 조건에 썼어요. 블록이 하나 늘어나지만, 계산 결과를 따로 확인할 수 있다는 장점도 있었어요.

**⑤ 조건에 맞는 문구 넣기**

해당하는 알림 문구(비, 추위, 일교차)만 골라서 한 메시지에 모으는 부분이에요.
Make는 메시지 칸 안에 `if(조건; 맞으면; 아니면)` 수식을 써서 노코드로 해결했어요.
Activepieces는 메시지 칸에 이런 조건 수식이 없어서 노코드로는 만들 수 없었어요. 그래서 AI에게 코드를 받아 **Code 블록**에 넣어 해결했어요. (한계기록서 [한계 1], 코드 시도 기록 참고)

**⑥ 테스트 방법**

Make는 **Run once**를 누르면 처음부터 끝까지 한 번에 실행되고, 블록마다 생기는 말풍선을 눌러 들어온 값과 나간 값을 볼 수 있어요.
Activepieces는 블록마다 **Test step**으로 하나씩 테스트하고, 전체 실행은 **Test Flow**로 따로 해요. 블록 하나만 바로 확인할 수 있어서 편하지만, 블록을 하나씩 테스트했다고 해서 전체가 이어서 잘 돌아간다는 보장은 없어서 전체 실행도 꼭 해 봐야 했어요.

### 그 밖에 확인한 차이 (참고)

| 항목 | Make | Activepieces |
|---|---|---|
| 데이터 넣는 방법 | `{{ }}` 수식을 직접 쓰거나 붙여 넣기 | 데이터 선택 창에서 값을 클릭해서 넣기 |
| 텔레그램 메시지 형식 | 기본 설정으로 바로 전송됨 | 괄호와 점이 든 메시지에서 HTTP 400 오류가 나서 Format을 HTML로 바꿈 |
| 스케줄 설정 | 첫 블록의 시계 아이콘에서 Daily, 시간 입력 | Schedule 트리거 블록(Every Day)에서 시간과 시간대 입력 |
| 무료 사용량 | 한 달 1,000 크레딧, 활성 시나리오 2개 | 한 달 1,000 크레딧 |
| 실행 기록 확인 | 시나리오 상세 페이지의 History | 프로젝트의 Runs 탭 |
| 자동 실행 켜기 | 시나리오를 Active로 켬 | Publish로 게시해야 켜짐 |

## 6. 도구별 장단점

### Make

**장점**
- 조건 칸이나 메시지 칸에 수식을 바로 쓸 수 있어서, 일교차 계산이나 해당 문구만 넣는 기능을 **블록을 더 늘리지 않고 노코드로** 해결할 수 있었다.
- "이상/이하" 연산자가 있어서 정한 기준값(60%, 0도, 10도)을 **그대로** 쓸 수 있었다.
- Run once 한 번으로 전체가 실행되고, 블록마다 말풍선으로 결과를 볼 수 있어서 **어디까지 실행됐는지 바로 알 수 있었다.**

**단점**
- `{{first(1.data.daily.temperature_2m_min)}}`처럼 수식을 직접 써야 해서, **수식 문법을 모르는 초보자는 혼자 만들기 어렵다.**
- 블록을 자유롭게 끌어서 연결하는 방식이라, 연결이 잘못 붙어도 **겉보기에는 티가 잘 안 난다.**
- 무료 요금제는 켜 둘 수 있는 시나리오가 2개뿐이고, 자동 실행 간격이 최소 15분이다.

### Activepieces

**장점**
- 블록이 위에서 아래로 쌓여서 **실행 순서가 한눈에 보이고**, Router를 쓰면 길이 갈라지는 모양이 화면에 그대로 보인다.
- 데이터 선택 창에서 값을 **클릭해서 넣는 방식**이라 수식을 몰라도 값을 연결할 수 있다.
- 블록마다 Test step으로 하나씩 확인할 수 있어서, 문제가 생겼을 때 **어느 블록이 문제인지 찾기 쉽다.**
- 무료 요금제에서도 Code 블록을 쓸 수 있어서, 노코드로 안 되는 부분을 코드로 보완할 수 있었다.

**단점**
- "이상/이하" 연산자가 없어서 **기준값을 59, 0.1, 9.9로 바꿔야 했다.** 값이 소수 몇 자리인지까지 생각해야 해서 번거로웠다.
- 조건 칸에서 계산이 안 되고, 메시지 칸에 조건 수식도 없어서 **Make에서는 노코드로 되던 기능에 블록을 더 넣거나 코드를 써야 했다.**
- 텔레그램 메시지 형식(HTML) 설정이나 Publish를 해야 켜지는 것처럼, **처음 쓰는 사람이 모르고 지나치기 쉬운 설정**이 있었다.

## 7. 어떤 상황에 적합한지 (내 의견)

전체적으로는 **Make가 더 쓰기 편했다.** 같은 기능을 만드는 데 블록 수도 적었고, 코드 없이 끝까지 만들 수 있었기 때문이다.

- **Make가 적합한 상황:** 계산이나 조건이 여러 개 들어가는 자동화를 **코드 없이** 만들고 싶을 때. 수식 문법만 조금 익히면, 블록 하나 안에서 계산과 조건 처리를 다 할 수 있어서 흐름이 단순해진다.
- **Activepieces가 적합한 상황:** 자동화를 **처음 배우는 사람**이 흐름을 차근차근 이해하면서 만들 때. 순서가 눈에 잘 보이고 블록마다 테스트할 수 있어서 배우기 좋다. 또 노코드로 부족한 부분을 **코드로 보완해야 할 때**나, AI 블록을 무료로 써 보고 싶을 때도 잘 맞는다.
